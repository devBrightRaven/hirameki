# Hirameki コマンド — 完全仕様

すべての Hirameki コマンドの完全な prompt 仕様。これは人間が読むためのリファレンス — 実際のコマンド prompt は `commands/` フォルダにあります。

---

## 共用：`__init`

すべてのコマンドは、まず `~/.claude/vault-local.md` の `vault:` で vault ルートを解決し、次に `<vault>/AGENTS.md` の `## Vault Structure` セクションからフォルダーパスを読み込みます（フォールバック：`~/.claude/vault-local.md`、次に `~/.claude/CLAUDE.md`）。

### Vault の検出

1. 現在の作業ディレクトリに `.obsidian/` が存在 → それを vault として使用
2. `~/.claude/CLAUDE.md` の `## Vault` セクションの `path` 設定を読み込む
3. Obsidian の `obsidian.json`（OS 別パス）を読み込む。組み込み sandbox パスを除外。複数の vault が見つかった場合はユーザーに選択を求める
4. 見つからない場合 → ユーザーにパスを確認、`.obsidian/` があることを検証、`~/.claude/CLAUDE.md` に書き込む

### 言語の検出

`vault-local.md` の `## Vault Structure` の `language` 設定を読み込む。すべての出力にこの言語を使用。

### フォルダーの検出

各目的ごとに、最初に存在する候補フォルダーを使用：

| 目的 | 候補名 |
|------|--------|
| daily | `_yorozuya/daily/`, `Daily/`, `_daily/`, `daily/`, `Journal/`, `journal/` |
| inbox | `Inbox/`, `_inbox/`, `inbox/`, `_Capture/`, `Capture/` |
| research | `_yorozuya/research/`, `_hirameki_analysis/`, `_agent_analysis/`, `Analysis/`, `_analysis/`, `analysis/` |
| journal | `_yorozuya/journal/`, `_hirameki_logs/`, `_agent_logs/`, `Logs/`, `_logs/`, `logs/` |
| handoff | `_yorozuya/handoff/`, `Handoff/`, `_handoff/`, `handoff/` |
| templates | `Templates/`, `_templates/`, `templates/` |

見つからない場合：ユーザーに確認、フォルダーを作成、完全なパスを出力、`<vault>/AGENTS.md` に書き込む。

### コンテンツフォルダー

「コンテンツフォルダー」= vault ルート直下のすべてのトップレベルフォルダー。ただし除外：
- `.` で始まる隠しフォルダー（`.obsidian/`、`.git/` など）
- `_hirameki_cmds/`
- `## Vault Structure` に記載されたシステムフォルダー

コンテンツフォルダーがない場合：vault ルート直下のすべての `.md` ファイルをスキャン。

## Orchestrators（オーケストレーター）

### `/hirameki:triage`

**目的：** セッション終了バンドル — wrap、journal、handoff を一つのガイド付きフローにまとめる。
**入力：** なし。セッション終了時に実行。

#### 共有セッション状態の収集（一度だけ実行）

最初のサブフローの前に、以下からセッションコンテキストを収集：
- このセッションで作成または修正されたファイル（Edit/Write 履歴）
- 完了・未完了のタスク（TaskList）
- このセッションで行われた主要な決定

3 つのサブフローすべてがこの状態を共有。

#### [1/3] Wrap

wrap のロジックを実行（`/hirameki:wrap` 仕様参照）。完全なドラフトと書き込み先を表示。次に：

```
[1/3] Wrap — Action? (save / skip / edit)
```

- `save` → `{daily}/YYYY-MM-DD.md` に書き込み、[2/3] へ
- `skip` → 書き込まず、[2/3] へ
- `edit` → 「どの部分を修正しますか？」と確認 → ドラフト調整 → 更新されたドラフトを表示 → save/skip

#### [2/3] Journal

journal のロジックを実行（`/hirameki:journal` 仕様参照）。セッション活動からトピックを推定。完全なドラフトと書き込み先を表示。次に：

```
[2/3] Journal — Action? (save / skip / edit)
```

同じ save/skip/edit パターン。選択に関わらず [3/3] へ進む。

#### [3/3] Handoff

handoff のロジックを実行（`/hirameki:handoff` 仕様参照）。完全なドラフトと書き込み先を表示。次に：

```
[3/3] Handoff — Action? (save / skip / edit)
```

完了後、完了サマリーを表示：

```
Triage 完了：wrap ✓ / journal – / handoff ✓
```

**ルール：**
- 各ステップで常に完全なドラフトを表示 — コンテンツの量で自動スキップしない
- skip はフローを中断しない。常に次のサブフローへ進む
- 各サブフローの書き込みロジック（同日追記 vs. 新規作成）はそのプリミティブのルールに従う

### `/hirameki:lens <概念>`

**目的：** トピックの理解 — arc、ポジション抽出、bridge、challenge の四ステップフロー。
**入力：** 単一のトピックまたは概念（必須）。空の場合は確認。

開始前に出力：
```
Lens on: {概念}
```

#### Step 0 — 共有コンテキスト（一度だけ実行）

vault 内のトピックをスキャン。収集：
- トピックに言及するすべてのファイル
- 最古・最新のファイル日付（arc タイムライン用）
- このトピックとよく一緒に出現する関連トピック（bridge パートナー提案用）

#### [1/4] Arc

共有コンテキストを使って arc のロジックを実行（`/hirameki:arc` 仕様参照）。次に：

```
[1/4] Arc — Action? (save / skip / next)
```

- `save` → `{research}/lens/YYYY-MM-DD-{概念}-arc.md` に書き込み
- `skip` または `next` → [2/4] へ

#### [2/4] ポジション抽出

vault からこのトピックに関するすべての明示的な立場・主張を抽出。

ルール：
- このトピックに直接関係する主張のみ — 周辺的な言及は除外
- ソースごとに一つの主張 — 最も具体的または明確なもの
- 上限：10 の最も関連性の高いソース
- 純粋な抽出のみ — 文体での回答は作成しない

出力：

```
## ポジション一覧：{概念}

> 分析時間：YYYY-MM-DD HH:MM

| ソース | 主張 |
|--------|------|
| [[ファイル名]] | その立場または主張（一文） |

### テンション
（2つ以上の主張が矛盾する場合、テンションを指摘。
すべての主張が同じ方向を向いている場合：「顕著なテンションは見当たらない」。）

### ギャップ
（このトピックについて vault で扱われていない角度。）
```

次に：

```
[2/4] ポジション — Action? (save / skip / next)
```

- `save` → `{research}/lens/YYYY-MM-DD-{概念}-positions.md` に書き込み

#### [3/4] Bridge

最も可能性の高いパートナートピックを自動提案（Step 0 で最も頻繁に共起したもの、または arc の空白地帯の最も顕著なもの）。実行前に提案を表示：

```
[3/4] Bridge — パートナートピックの提案：{suggested}
  Action? (save / skip / change-partner)
```

- `save` または Enter → 承認、bridge ロジックを実行、出力を表示、最終保存を確認
- `skip` → [4/4] へ
- `change-partner` → 「{概念} を何とブリッジしますか？」と確認 → bridge を実行

Bridge のロジックは `/hirameki:bridge` 仕様と同様。保存先：`{research}/lens/YYYY-MM-DD-{概念}-bridge.md`

#### [4/4] Challenge

[2/4] で抽出したポジションを使って challenge のロジックを実行（`/hirameki:challenge` 仕様参照）。次に：

```
[4/4] Challenge — Action? (save / skip / next)
```

- `save` → `{research}/lens/YYYY-MM-DD-{概念}-challenge.md` に書き込み

4 ステップすべて完了後：

```
Lens 完了：arc {✓ 保存 | – スキップ} / ポジション {✓ 保存 | – スキップ} / bridge {✓ 保存 | – スキップ} / challenge {✓ 保存 | – スキップ}
```

### `/hirameki:compose <トピック>`

**目的：** トピックの創作 — 文体での回答とフレームテストの二ステップフロー。
**入力：** トピックまたは質問（必須）。空の場合は確認。
**スタンドアロン：** `/hirameki:lens` を先に実行する必要はない。

開始前に出力：
```
Compose on: {トピック}
```

#### [1/2] Voice（文体での回答）

完全な reflect のロジックを実行（`/hirameki:reflect` 仕様参照）：
1. コンテンツフォルダーの完成記事から文章スタイルを分析
2. vault からこのトピックに関するポジションを抽出（上限：5 ソース）
3. 特定したスタイル + ポジションを使って著者の文体で回答を作成

出力は `/hirameki:reflect` 仕様と同様（回答 / ソース / 確信度）。次に：

```
[1/2] Voice — Action? (save / skip / edit-question)
```

- `save` → `{research}/compose/YYYY-MM-DD-{トピック}-voice.md` に書き込み
- `skip` → [2/2] へ
- `edit-question` → 「修正したトピックまたは質問は？」と確認 → Voice ステップを再実行

#### [2/2] Frame（フレームテスト）

Voice の出力を評価対象のアイデアとして frame のロジックを実行（`/hirameki:frame` 仕様参照）。[1/2] がスキップされた場合、「どのアイデアをフレームしますか？」と確認して入力を待つ。

完全な五問テスト + 判定出力。次に：

```
[2/2] Frame — Action? (save / skip / next)
```

- `save` → `{research}/compose/YYYY-MM-DD-{トピック}-frame.md` に書き込み

両ステップ完了後：

```
Compose 完了：voice {✓ 保存 | – スキップ} / frame {✓ 保存 | – スキップ}
```

### `/hirameki:mekiki <入力>`

**目的：** 外部リソースのキャプチャ — リポジトリか記事かを自動検出。
**入力：** 必須 — GitHub URL、記事 URL、貼り付けたテキスト、またはローカルファイルパス。

#### 入力ルーティング

| 入力の形 | ブランチ |
|---------|---------|
| `github.com/[^/]+/[^/]+` または `^[^/]+/[^/]+$` に一致 | リポジトリブランチ |
| その他の URL（`http(s)://`） | 記事ブランチ（URL） |
| ローカルファイルパス（`/`、ドライブレター、`./` で始まり、ファイルシステムに存在） | 記事ブランチ（ファイル） |
| その他 | 記事ブランチ（貼り付け） |

検出順序：リポジトリパターン → URL → ファイルパス → 貼り付け。

#### リポジトリブランチ

**フェーズ 1 — フェッチ（並列）：**
```bash
gh repo view owner/repo --json description,url,stargazerCount,primaryLanguage,updatedAt
gh api repos/owner/repo/readme -q .content | base64 -d
gh api repos/owner/repo/git/trees/HEAD?recursive=1 -q '.tree[].path' | head -150
```
3–5 の主要ソースファイルを特定してコンテンツをフェッチ。

**フェーズ 2 — 分析：**

Track A — テクニック抽出（常に実行）：各興味深いパターンについて抽出：パターン名、何か（1–2 文）、なぜ興味深いか、どこに転用できるか（ユーザーの実際のプロジェクト）、具体的な次のステップ。

Track B — 採用評価（純粋なデモ/パターンリポジトリはスキップ）：ユーザーの CLAUDE.md とプロジェクトメモリを読み込む。リポジトリをツール/フレームワーク/ライブラリ/パターンとして分類。比較表を作成（機能 / リポジトリが提供するもの / 現在使用しているもの / ギャップ）。判定：**adopt**（次のステップとタイムライン付き）/ **defer**（トリガー条件付き）/ **reject**（代替案付き）。

**フェーズ 3 — 検証（Sonnet サブエージェント）：** 完全性、信頼性、実行可能性を確認。10 ファイル未満の小規模リポジトリはスキップ。

**書き込み：** `{research}/mekiki-{リポジトリ名}.md` — フロントマター：`tags: [mekiki, {判定}]`、`status: reference`、`source: claude-code`。

#### 記事ブランチ

**フェーズ 1 — ソースのキャプチャ：**
- URL → WebFetch
- ファイル → Read
- 貼り付けテキスト → そのまま使用

抽出：タイトル、著者、日付、核心的な主張（1–3 文）、重要な主張のリスト、vault にない語彙・概念。

ソースノートを `{inbox}/YYYY-MM-DD-{slug}.md` に書き込み：
```yaml
---
tags:
  - inbox
  - mekiki
status: draft
source: external
created: YYYY-MM-DD
url: {ソース URL（あれば）}
---
```

**フェーズ 2 — クロスリファレンス：** コンテンツフォルダーと最近の wrap logs をスキャンし、同じ主張や概念に触れている vault ノートを検索。各一致：`[[ファイル名]]` + この記事との関係（支持 / 矛盾 / 拡張 / 拡張される）。

**フェーズ 3 — 判定：**

```
## 統合する価値はあるか？

**判定：** integrate / revisit-later / skip
**理由：** 一文
**次のステップ：** 一つの具体的なアクション（例：概念カードの作成、執筆アウトラインへの追加、特にアクション不要）
```

書き込み後、inbox ファイルパスを出力。

## セッション

### `/hirameki:next`

**目的：** セッション再開後の定位。
**入力：** なし。
**ファイルへの書き込みなし。**

このセッションのタスクリスト、ファイル活動（作成または修正されたファイル）、行われた決定、プッシュしたコミットをスキャン。簡潔な定位サマリーを出力：完了した作業、未処理事項、次のステップ。

---

### `/hirameki:wrap [説明]`

**目的：** 進捗スナップショット、wrap log に追記。
**入力：** オプションの重点説明。
**必要なフォルダー：** daily、templates。

セッションのファイル操作（作成、修正、削除）と今日の wrap log をスキャン。

書き込み先：`{daily}/YYYY-MM-DD.md`
- ファイルが存在しない + `templates/daily.md` が存在 → テンプレートを使用
- ファイルが存在しない、テンプレートなし → `# YYYY-MM-DD` 見出しを作成
- ファイルが存在する → 水平線の後に新しい Wrap ブロックを追記

Wrap 形式：

```
---

## Wrap [HH:MM]

### 完了
- [このセッションで完了した具体的な項目、各一文]

### 進行中
- [開始したが未完了の項目。なければ「なし」]

### 次のステップ
- [次にすること。未定の場合「未定」]
```

ルール：
- タイムスタンプはローカル時間 HH:MM（24 時間制）
- 追記のみ — 以前の Wrap ブロックは修正しない
- 入力説明がある場合、それを使って Wrap コンテンツを整理
- 書き込み前にドラフトと完全なパスを表示し、確認後に実行；実行後に実際のパスを出力

---

### `/hirameki:journal <説明>`

**目的：** 作業ログと推論記録。
**入力：** トピック説明（必須）。
**必要なフォルダー：** journal + すべてのコンテンツフォルダー（関連ノートの検索用）。

スキャン：このセッションの操作、トピックに関連する vault ノート、今日の journal 内の既存ファイル。

ロジック：
1. `{journal}/` 内の今日の `YYYY-MM-DD-*.md` ファイルをスキャン
2. ファイル名とタイトルを入力トピックのキーワードと照合
3. 明確な一致 → 追記モード
4. 曖昧な一致 → 候補を一覧表示し、ユーザーに確認
5. 一致なし → 作成モード

**作成モード** — `{journal}/YYYY-MM-DD-HHMM-{トピックスラッグ}.md` に書き込み：

```
# {トピック}

> 作成時間：YYYY-MM-DD HH:MM

## 背景
なぜこれが起きたのか。既存の vault ノートがあれば [[wiki link]] で参照。

## 何をしたか
具体的な操作と決定、因果関係の説明付き。

## なぜそのアプローチを選んだか
主要な決定の理由。トレードオフ：何を選び、何を諦めたか。

## インスピレーションのつながり
他のアイデアとのつながり。[[wiki link]] で関連ノートを参照。なければ「なし」。

## 改善の可能性
探索していない方向性、代替案、潜在的なリスク。なければ「なし」。

## 未完了と後続
フォローアップが必要な項目。すべて完了の場合「未完了事項なし」。
```

**追記モード** — 末尾に追加：

```
---

## 追記 [HH:MM]

### 何をしたか
[新しい操作と決定]

### なぜそのアプローチを選んだか
[新しい理由]

### インスピレーションのつながり
[新しいつながり。なければ「なし」]

### 改善の可能性
[新しい方向性。なければ「なし」]
```

「未完了と後続」も確認 — 完了した項目にはタイムスタンプを付ける。

### `/hirameki:handoff`

**目的：** 次のセッションのための引き継ぎ文書。
**入力：** なし。トピックとスラッグはセッション活動から推定。
**必要なフォルダー：** handoff。

収集：このセッションで作成または修正されたファイル、完了・未完了のタスク、主要な決定、遭遇したブロッカー。

セッション活動の主要なテーマからトピックを推定。曖昧な場合はユーザーに確認。

書き込み先：`{handoff}/YYYY-MM-DD-{slug}.md`

```yaml
---
tags:
  - handoff
status: log
source: claude-code
created: YYYY-MM-DD
---
```

```
# Handoff：{トピック} — {YYYY-MM-DD}

> セッション終了：YYYY-MM-DD HH:MM

## 完了したこと
- [完了項目]

## 現在の状態
[現在の状況 — 途中のもの、待機中のもの]

## 未完了スレッド
- [未完了項目] — [残っていること]

## 主要な決定
- [決定] — [理由]

## 次のセッション：ここから始める
1. [最初に引き継ぐこと]
2. [2つ目、あれば]

## 注意事項
[次のセッションが間違いや重複作業を避けるために必要な情報。なければこのセクションを省略。]
```

書き込み前に完全なドラフトと書き込み先を表示。書き込み後にパスを出力。

## 理解（スタンドアロン）

### `/hirameki:arc <概念>`

**目的：** vault 全体でその概念がどのように進化したかを追跡。
**入力：** 概念またはトピック（必須）。
**必要なフォルダー：** research + すべてのコンテンツフォルダー。

ロジック：
1. `{research}/arc/` に今日の同じ概念のファイルがあるか確認
2. 見つかった → 追記モード；見つからない → 作成モード

**作成モード** — `{research}/arc/YYYY-MM-DD-{概念}.md` に書き込み：

```
# 概念トラッキング：{概念}

> 分析時間：YYYY-MM-DD HH:MM

## 最初の登場
この概念が最初に登場したファイルとコンテキスト。関連する段落を最大 3 文引用。
日付：YYYY-MM-DD

## 進化のタイムライン
- YYYY-MM-DD | [[ファイル名]] | そのファイルでのこの概念の使い方や立場（一行）

## 現在の状態
この概念が現在つながっているトピック、矛盾した使い方、発展中の draft。

## 未探索の角度
この概念のどの側面が vault でまだ扱われていないか。
```

**追記モード** — 末尾に追加：

```
---

## トラッキング更新 [HH:MM]

### タイムライン（新規）
- [前回の分析以降に新しく登場した言及]

### 状態変化
```

## 創作（スタンドアロン）

### `/hirameki:frame <アイデア>`

**目的：** 制作前チェックポイント — アイデアが追求する価値があるかを評価。
**入力：** 必須 — 記事のアイデア、プロダクトコンセプト、デザイン方向性、または既存 draft のパス。
**必要なフォルダー：** すべてのコンテンツフォルダー + wrap logs + journal。

#### フェーズ 1：アイデアの理解

入力シグナルからタイプを判定（記事 / プロダクト / デザイン）。ファイルパスの場合はファイルを読み込んで主張を抽出。主張とタイプを出力してから続行。

#### フェーズ 2：五問フレームテスト

**Q1 — Only-I テスト：**「このアイデアは私にしか言えない・できないことが何かあるか？」
vault 内の固有の経験・スキル・立場をスキャン。評価：強 / 弱 / なし。

**Q2 — 衝突スキャン：**「すでに同様のものを作ったことがあるか？」
- Tier 1（発表済み）：吸収済み / 隣接 / 置き換え済み。Tier 1「吸収済み」→ KILL トリガー。
- Tier 2（ドラフト）：競合 / 隣接 / 素材。CONSOLIDATE の問いをトリガー、KILL はトリガーしない。

**Q3 — 賭け：**「これに出会った後、読者/ユーザーに何が変わるか？」
再フレーミング / 道具を与える / 思考を刺激 / 上記のいずれでもない。「情報提供だけ」= 賭けが低すぎる。

**Q4 — テンション：**「驚くべき・直感に反する・不快な部分は何か？」
著者が受け入れる矛盾 / 逆転 / 告白。テンションなし = 要約であり、創作ではない。

**Q5 — 証拠：**「どのような実体験・データ・具体的な例がこの論証を信頼できるものにするか？」
体験済み / 研究に基づく / 推測的。

#### フェーズ 3：判定

| 判定 | 条件 |
|------|------|
| **PROCEED** | Q1 強 + Q3/Q4 少なくとも一つ強 + Tier 1 吸収済み衝突なし |
| **RETHINK** | Q1 弱、または隣接衝突、または Q3「情報提供のみ」 |
| **KILL** | Q1 なし、または Tier 1 吸収済み、または Q3 と Q4 の両方が空 |
| **CONSOLIDATE** | Q2 に複数の Tier 2 競合 draft あり |

```
## Frame：PROCEED
**主張**：[一文]
**ユニークな角度**：[Q1 から]
**核心のテンション**：[Q4 から]
**主要な証拠**：[Q5 から]
### 開始前に
- [確定すべき 1–2 の具体的なこと]

## Frame：RETHINK
**主張**：[一文]
**問題**：[どの問いが失敗したか、なぜ]
### これをやる価値が出るには
- [1–3 の具体的な方向性]
### 土台にできる既存作品
- [[ファイル名]] — [関連する理由]

## Frame：KILL
**主張**：[一文]
**理由**：[一文]
**救える部分**：[保持する価値のある断片、または「なし」]

## Frame：CONSOLIDATE
**主張**：[一文]
**競合 draft**：
- [[draft 1]] — 強み：X、弱み：Y
**推奨メイン vessel**：[[最も強い draft]] — [理由]
**他の draft から吸収する部分**：[具体的なコンテンツ]
**統合後に引退させる draft**：[リスト]
```

ルール：判定を和らげない。KILL は止まれを意味する。`save` 付き → `{research}/frame/YYYY-MM-DD-{アイデアスラッグ}.md` に書き込み。frame はコンテンツを生成しない。

2. 重複除去とランク付け：正規化し、類似タスクをグループ化、頻度順に並べ、次に最近出現した順
3. 出力：ソース付きの順序リスト。3 回以上出現する項目に ⚠ プレフィックスを付ける。

#### Stuck モード — `tasks stuck [N]`

N 日間（デフォルト 7）をスキャン。「次のステップ」ブロックに 2 回以上出現し、「完了」ブロックには一度も現れないタスクを探す。分類：**blocked（ブロック）** / **deferred（延期）** / **forgotten（忘れた）** / **persistent（継続中）**。

ルール：読み取り専用、ファイルは修正しない。

## メンテナンス

### `/hirameki:tidy [tags|fix|full|lint]`

**目的：** フロントマターの健全性チェックとクリーンアップ。
**入力：** オプションのモード引数。
**必要なフォルダー：** すべてのコンテンツフォルダー + inbox + daily-notes。

**モード：**

| 呼び出し方 | 実行内容 |
|-----------|---------|
| `tidy`（引数なし） | 欠落フィールド + 一致性チェック |
| `tidy tags` | タグ収束分析のみ |
| `tidy fix` | 欠落フィールド + 一致性 + 自動修正 |
| `tidy full` | すべてのチェック |
| `tidy lint` | コンテンツ健全性チェックのみ |

**スキャン範囲：** すべてのコンテンツフォルダー（再帰的）、すべての inbox ファイル、wrap logs（最近 30 日間）。

#### 欠落フィールドチェック（tidy / fix / full）
- フロントマターのないファイル
- フロントマターはあるが `tags` または `status` がない
- `tags` が空の配列または空白；`status` が空白

#### 一致性チェック（tidy / fix / full）
- `status` が許可値にない：`published`、`draft`、`reference`、`outline`、`spec`、`log`、`archive`
- `source` が許可値にない（フィールドが存在する場合）：`self`、`claude-code`、`agent`、`external`
- 同義タグの大文字小文字不一致（例：`AI-alignment` vs `ai-alignment`）
- タグのアンダースコアとハイフンの不一致
- `topic` と `tags` 間の明らかな重複

#### 冗長性チェック（full のみ）
- 6 つ以上のタグを持つファイル
- `created` フィールドの形式が不一致（YYYY-MM または YYYY-MM-DD であるべき）

#### タグ収束分析（tags / full）
vault 全体のタグ使用状況をカウント：
- 最も使われている上位 10 タグ（コアタグ）
- 意味的に類似しているが異なる名前のタグ（統合候補グループ）
- 一度しか出現しないタグ（孤立タグ — 各一覧表示）

#### コンテンツ健全性チェック — lint モードのみ

**矛盾の検出：** 同じトピックについて矛盾する主張をしているノートのペア。各：ノート A [[ファイル名]] — 主張；ノート B [[ファイル名]] — 矛盾する主張；深刻さ：直接矛盾 / テンション / 進化（著者が時間をかけて考えを変えた）。

**陳腐な主張：** `status: published` または `reference` で 90 日以上修正されていないノート。各：[[ファイル名]] — 最終修正日 — トピックサマリー — 質問：これはまだ正確か？

**孤立ノート：** 他のノートからの [[wiki link]] が一つもないノート（daily、inbox、システムフォルダーは除外）。各：[[ファイル名]] — 作成日 — トピック — 提案。

**デッドリンク：** 存在しないファイルを指している [[wiki link]]。各：ソース [[ソースノート]] — 壊れたリンクテキスト — 提案。

lint モードは読み取り専用。lint 出力後、いずれかの領域の N > 0 の場合、追加：

```
## クロスリファレンス提案

### 矛盾を深掘りする
（contradictions N > 0 のみ）
最も矛盾の多いトピックに対して `/hirameki:lens <トピック>` を実行して詳細な弱点分析。
最も矛盾が多いトピック：{トピック}

### Vault のパターンを表面化
（孤立タグ ≥ 5 または孤立ノート ≥ 5 のみ）
`/hirameki:pulse patterns` を実行して vault 全体の繰り返しテーマとギャップを確認。

### 陳腐な主張を処理
（stale claims N > 0 のみ）
まだ有効な主張：`/hirameki:graduate <ノート>` を実行して安定した概念カードに昇格。
古くなった主張：フロントマターの `status` を `archive` に更新。
注目が必要な陳腐なファイル：N 件
```

すべての領域が 0 の場合、クロスリファレンスセクションを完全に省略。

#### Fix ロジック（fix 入力時のみ）

計画されたすべての変更の完全なリストを表示。実行前に確認を待つ。

自動修正可能：
- 欠落したフロントマタースケルトンを追加（空のタグ + `status: draft`）
- タグの大文字小文字を正規化（多数決）
- タグのアンダースコアをハイフンに正規化
- `topic` と `tags` の重複を削除

項目ごとの確認が必要：
- 意味的に類似したタグの統合
- 6 つ以上のタグを持つファイルのトリミング
- 孤立タグの削除

修正後、健全性スコアを再計算し、差分サマリーを出力。

**書き込み：** `{research}/tidy/YYYY-MM-DD.md`。同日は更新を追記（健全性スコアの変化を含む）。1 回の実行で最大 50 問題を報告。

### `/hirameki:__init`

**目的：** 初回セットアップと vault 設定。
**入力：** なし。

#### Mode A：初回セットアップ

`<vault>/AGENTS.md`、`vault-local.md`、`CLAUDE.md` のいずれにも `## Vault Structure` がない場合に実行。

**ステップ 1 — Vault の検出：** CWD → CLAUDE.md パス → obsidian.json（組み込み sandbox をフィルタリング）を試みる。複数ある場合はユーザーに選択を求める。見つからない場合：ユーザーに確認。

**ステップ 2 — 言語：** 確認：繁体字中国語 / English / 日本語 / その他。

**ステップ 3 — フォルダー解決：** 各目的を最初に存在する候補（上記フォルダー表参照）と照合。一致なしの場合：どこに作成するかユーザーに確認し、確認後に作成。

**ステップ 4 — 設定の書き込み：** 読み手ごとに 2 か所へ書き込みます。
```
# ~/.claude/vault-local.md  (マシン固有)
## Vault Structure
vault: {完全な vault パス}
language: {言語}
```
```
# {vault}/AGENTS.md  (vault と一緒に移動)
## Vault Structure
daily: {フォルダー名}/
inbox: {フォルダー名}/
research: {フォルダー名}/
journal: {フォルダー名}/
handoff: {フォルダー名}/
templates: {フォルダー名}/
```

**ステップ 5 — 共有 policies vault（オプション）：** 確認。はいの場合：パスを検証、シンボリックリンクを作成 `~/.claude/rules/policies/ → {policies パス}`、vault-local.md に `shared-policies: {パス}` を追加。

**ステップ 5b — 個人 policies vault（オプション）：** 確認。ステップ 5 と同様、`~/.claude/rules/personal/` を使用。

**ステップ 6 — リファレンス doc 同期：** `{vault}/_hirameki_cmds/` を確認。存在しない → 作成し、選択した言語のリファレンス doc をコピー。存在して空でない → 上書きするか確認。

言語マッピング：
- 繁体字中国語 → `hirameki-cmds-short-zh-TW.md` + `hirameki-cmds-full-zh-TW.md`
- 日本語 → `hirameki-cmds-short-ja.md` + `hirameki-cmds-full-ja.md`
- English またはその他 → `hirameki-cmds-short.md` + `hirameki-cmds-full.md`

#### Mode B：再設定

設定が既に存在する場合に実行。更新する内容を確認（言語 / 特定フォルダー / 共有 policies / 個人 policies / リファレンス doc / 最初からやり直す）。選択された項目のみ修正。言語と vault パスは `vault-local.md`、フォルダーパスは `<vault>/AGENTS.md` に書き込む。

## 共用ルール

- すべてのタイムスタンプはローカル時間 HH:MM（24 時間制）
- すべてのファイル参照は [[wiki link]] 形式
- すべての書き込みコマンドは実行前にプレビューと完全なパスを表示し、確認後に実行；実行後に実際のパスを出力
- 出力言語は `~/.claude/vault-local.md` の `## Vault Structure` から読み込む
- Vault パスは常に実行時に vault-local.md から、フォルダーは `<vault>/AGENTS.md` から解決 — ハードコードしない
