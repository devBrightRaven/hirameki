# Hirameki コマンド — 完全仕様

すべての Hirameki コマンドの完全な prompt 仕様。これは人間が読むためのリファレンス — 実際のコマンド prompt は `commands/` フォルダにあります。

---

## 共通：`__init`

すべてのコマンドは最初に `~/.claude/CLAUDE.md` の `## Vault Structure` セクションを読み込みます。

### Vault 検出

1. 現在の作業ディレクトリに `.obsidian/` があるか確認 — あればそこが vault
2. なければ `~/.claude/CLAUDE.md` の `## Vault` セクションの `path` 設定を読む
3. どちらもなければ、ユーザーに vault パスを尋ね、`.obsidian/` を含むことを確認して `~/.claude/CLAUDE.md` に保存

### 言語検出

`~/.claude/CLAUDE.md` の `## Vault Structure` 下の `language` 設定を読む。すべての出力はこの言語で行う。

### フォルダ検出

各用途について、候補から最初に存在するフォルダをマッチ：

| 用途 | 候補 |
|------|------|
| daily-notes | `Daily/`, `_daily/`, `daily/`, `Journal/`, `journal/` |
| inbox | `Inbox/`, `_inbox/`, `inbox/`, `_Capture/`, `Capture/` |
| analysis | `_hirameki_analysis/`, `_agent_analysis/`, `_claude_code_analysis/`, `Analysis/`, `_analysis/`, `analysis/` |
| logs | `_hirameki_logs/`, `_agent_logs/`, `_claude_code_logs/`, `Logs/`, `_logs/`, `logs/` |
| templates | `Templates/`, `_templates/`, `templates/` |

見つからない場合：ユーザーに確認、フォルダを作成、完全パスを表示、`~/.claude/CLAUDE.md` の `## Vault Structure` に保存。

2回目以降は `## Vault Structure` のキャッシュ設定を直接読み込む。

### コンテンツフォルダ

「コンテンツフォルダ」= vault ルート直下の全フォルダから以下を除いたもの：
- ドット始まりのフォルダ（`.obsidian/`・`.claude/`・`.git/` など）
- `_hirameki_cmds/`
- `## Vault Structure` に記載されているシステムフォルダ

コンテンツフォルダがない場合は vault ルートの全 `.md` ファイルをスキャン。

## セッション開始

### `/hirameki:next`

**目的：** セッション再開後の定位。
**入力：** なし。
**必要なフォルダ：** なし（セッション状態を読み込む）。

現在のセッションのタスクリスト・ファイル活動（作成または変更されたファイル）・下された決定・プッシュされたコミットをスキャン。簡潔な定位サマリーを生成：完了した作業・未処理の事項・次のステップ。

ファイルへの書き込みなし。

---

### `/hirameki:catchup [日数]`

**目的：** 進捗の引き継ぎ。
**入力：** オプション日数（デフォルト 1）。
**必要なフォルダ：** daily-notes・inbox。

読み込み：
- 最近の daily notes（デフォルト：昨日、または指定日数分）
- すべての inbox ファイル

ロジック：各 daily note の最後の Wrap ブロックを見つける。「進行中」と「次のステップ」を抽出。

出力：

**最近の進捗** — 最後の Wrap の進行中と次のステップ。daily note や Wrap ブロックがない場合は「進捗記録なし」と注記。複数日の場合：各日の最後の Wrap を時系列逆順でリスト。

**Inbox 保留中** — inbox ファイル：ファイル名・作成日・1 文の要約。上限 10 件。空の場合：「Inbox クリア」。

**フォーカス提案** — 今日推進する価値がある 1〜3 件。各件に理由付き（なぜ今日なのか）。最大 3 件。

## セッション終了

### `/hirameki:wrap [説明]`

**目的：** 進捗スナップショットを daily note に書き込む。
**入力：** オプションの重点説明。
**必要なフォルダ：** daily-notes・templates。

スキャン：
- 現在のセッションのファイル操作（作成・変更・削除）
- 今日の daily note

書き込み先：`{daily-notes}/YYYY-MM-DD.md`
- ファイルなし + `templates/daily.md` あり → テンプレートを使用
- ファイルなし + テンプレートなし → `# YYYY-MM-DD` ヘッダーで作成
- ファイルあり → 水平線区切りで末尾に新しい Wrap ブロックを追記

各 Wrap のフォーマット：

```
---

## Wrap [HH:MM]

### 完了
- [この期間に完了した具体的な項目、各1文]

### 進行中
- [開始したが未完了の項目。なければ「なし」と記入]

### 次のステップ
- [次にやること。未決定なら「未定」と記入]
```

ルール：
- タイムスタンプはローカル時間 HH:MM（24 時間制）
- 前の Wrap ブロックは変更せず、追記のみ
- 入力に説明がある場合はそれを使って Wrap の内容を整理
- 書き込み前にプレビューと完全パスを表示、確認後に実行
- 実行後に実際の書き込みパスを表示

## Vault の状態

### `/hirameki:pulse [week|patterns]`

**目的：** Vault の現況（3 つのモード）。
**入力：** なし / `week` / `patterns`
**必要なフォルダ：** daily-notes + 全コンテンツフォルダ（patterns モードは inbox も必要）。

#### 引数なしモード — 即時スナップショット

スキャン：
- 全コンテンツフォルダ（深さ 2 層）
- daily-notes 直近 7 日

出力：

**コンテンツテーマ** — 各コンテンツフォルダとサブフォルダ：名前・ノート数・ドラフト数・最終更新日。ステータス：アクティブ（7 日以内に更新）/ 休眠。

**最近の活動** — 直近 7 日に更新されたファイル、時系列逆順。各件：ファイル名・親フォルダ・更新時刻・変更種類（新規作成 / 修正 / 大幅改稿）。上限 15 件。

**Vault 概要** — 総ファイル数・コンテンツフォルダ数・直近 7 日でアクティブなフォルダ。

空のセクションは「なし」と表示（省略しない）。

#### `pulse week` — 週次レビューとギャップ分析

読み込み：
- 全コンテンツフォルダの直近 7 日の更新記録
- 直近 7 日の daily notes

出力：

**今週の進捗** — アクティブな各コンテンツフォルダ：名前・何を推進したか（ファイル変更から判断）・次のステップ。

**最近の動き** — 先週追加・更新されたノート、完成に近いもの。

**ギャップ分析** — daily notes の優先事項と実際のファイル変更を比較：
- 重要と言ったのに着手しなかった（優先と宣言したが対応するファイル変更なし）
- 言及しなかったのに時間を使った（ファイル変更はあるが daily notes で未言及）

3 日分未満の daily notes なら「記録不足、ギャップ分析が不正確な可能性あり」と注記。

#### `pulse patterns` — 潜流とクラスター分析

スキャン：全コンテンツフォルダ・daily-notes（直近 30 日）・全 inbox。

**潜流テーマ** — 繰り返し登場するが独立した記事のないテーマ。基準：3 つ以上の異なるファイルに出現、独立した記事や draft なし。各テーマ：
- テーマ名
- 出現数と関連ファイル数（最大 5 件を [[wiki link]] で引用）
- 評価：展開する価値がある？なぜ？
上限 10 件、出現頻度の降順。

**形成中のクラスター** — 共通の親カテゴリなしに類似概念を扱う 3 本以上のノートが異なる日付で書かれているグループ。各グループ：
- 提案するクラスター名
- 関連ノート（[[wiki link]]、上限 5 件）
- 共通テーマの要約（2〜3 文）
- 成熟度：高 / 中 / 低
- 推奨の発展方向：記事 / プロジェクト / 概念フレームワーク / 蓄積継続
上限 5 件、成熟度の降順。

### `/hirameki:tasks [日数|stuck]`

**目的：** daily notes と journal から次のアクションを集約。
**入力：** オプション — 日数（デフォルト 3）または `stuck` / `stuck N`。
**ファイルへの書き込みなし。**

#### デフォルトモード — アクション集約

最近の daily notes と journal をスキャン。

1. **収集**：過去 N 日分の `{daily}/YYYY-MM-DD.md` を読み込む（各 Wrap ブロックから「次のステップ」を抽出）。今日と昨日のすべての `{journal}/YYYY-MM-DD-*.md` を読み込む（完了マークのない「Open items」を抽出）。
2. **重複排除とランク付け**：正規化後、同一タスクをグループ化（ファジーマッチ）。出現数の降順、次に最近の出現日の降順でソート。
3. **出力**：出典参照付きの番号リスト。3 回以上登場するアイテムには ⚠ プレフィックス。

#### Stuck モード — `tasks stuck [N]`

N 日分をスキャン（デフォルト 7）。「次のステップ」セクションに 2 回以上登場し、「完了」セクションには一度も現れていないタスクを発見。カテゴリ分け：**blocked（ブロック中）** / **deferred（先送り）** / **forgotten（放置）** / **persistent（継続中）**。

ルール：読み取り専用。入力を求めず即実行。

## 深掘り

### `/hirameki:lucky [n]`

**目的：** コンステレーション（星座）リーディング — ランダムなノートが隠れたテーマを明かす。
**入力：** オプション — 抽出するノート数（デフォルト 5、範囲 2–20）。
**ファイルへの書き込みなし。**

コンテンツフォルダから N 件のノートをランダム抽出：
- **ウェイト 3×**：30 日以上更新されていない放置ノート
- **ウェイト 1×**：直近 30 日に更新されたノート
- **除外**：システムフォルダ・`_hirameki_cmds/`・daily・inbox・research・journal

各ノートを最大 500 語読み込む。

**分析：** これらの N 件のノートの中心にある概念や問いを探す — 表面的なキーワードマッチではなく、すべてのノートを生み出しえた根底の緊張や未解決の執念。

**出力フォーマット：**

```
# Constellation: [日付]

> 抽出時間：YYYY-MM-DD HH:MM
> 抽出ノート数：N

[[ノート1]], [[ノート2]], [[ノート3]], [[ノート4]], [[ノート5]]

## 隠れたテーマ
[3〜5 文。どのノートがどの側面を示しているかを [[wiki link]] で引用。]

## あなたが問いかけているかもしれない問い
[1 つの問い — これらのノートが直接述べることなく周回しているもの。]
```

ルール：すべての参照は [[wiki link]] 形式。問いは 1 文のみ。ノートに共通点がない場合は直接述べる — つながりを捏造しない。

### `/hirameki:explore {入力} [save]`

**目的：** 概念の発掘 — 入力の形からモードを自動判断。
**入力：** 必須。形がモードを決定。末尾に `save` を追加でファイルに書き込み。
**必要なフォルダ：** analysis + 全コンテンツフォルダ。

#### モード判定

| 入力の形 | モード |
|----------|--------|
| 単一の概念またはキーワード | **Arc** |
| 2 つのテーマを「と」「and」「與」で区切る | **Bridge** |
| `?` や `？` で終わる | **Ghost** |
| `test:` で始まる | **Stress-test** |

#### Arc モード — 概念進化の追跡

スキャン：vault 全体、daily-notes とコンテンツフォルダを優先。

ロジック：
1. `{analysis}/arc/` で今日の同概念ファイルを確認
2. マッチあり → 追記モード
3. 曖昧なマッチ → 候補をリスト、ユーザーに確認
4. マッチなし → 新規作成モード

**新規作成モード** — `{analysis}/arc/YYYY-MM-DD-{概念}.md` に書き込み：

```
# 概念追跡：{概念}

> 分析時間：YYYY-MM-DD HH:MM

## 初出
この概念が最初に登場したファイルと文脈。関連段落を最大 3 文引用。

## 進化タイムライン
- YYYY-MM-DD | [[ファイル名]] | そのファイルでの使われ方/立場の1文要約

## 現在の状態
この概念がどのトピックに接続しているか、矛盾する使われ方、発展中の draft があるか。

## 空白地帯
この概念の中で vault でまだ探求されていない側面。
```

**追記モード** — 既存ファイルの末尾に追加：

```
---

## 追跡更新 [HH:MM]

### 進化タイムライン（新規）
- [前回の分析以降の新しい言及]

### 状態の変化
- [何が変わったか。変化がなければ「顕著な変化なし」と記入]

### 空白地帯（更新）
- [未探求の側面を再評価]
```

#### Bridge モード — 2 テーマ間の隠れたつながり

スキャン：vault 全体。

ロジック：
1. `{analysis}/bridge/` で今日の同テーマペアのファイルを確認（順序不問）
2. マッチあり → 追記；なし → 新規作成

**新規作成モード** — `{analysis}/bridge/YYYY-MM-DD-{テーマA}-と-{テーマB}.md` に書き込み：

```
# 橋接分析：{テーマA} と {テーマB}

> 分析時間：YYYY-MM-DD HH:MM

## 直接の交点
両テーマに言及しているファイル。各件：[[ファイル名]]・2 つのテーマがそのファイルでどう関連しているか。
なければ「直接の交点なし」と記入。

## 橋渡しノート
片方のテーマのみ言及しているが、リンクを形成しうるファイル。なぜ橋渡しになりうるか説明。
上限 5 件、各件 [[wiki link]] で引用。

## 潜在的なつながり仮説
深層のつながりに関する 1〜3 件の仮説。各件：強 / 中 / 弱の信頼度と根拠。
```

**追記モード：**

```
---

## 追跡更新 [HH:MM]

### 新しい交点
- [前回の分析以降の新しい交点または橋渡しノート]

### 仮説の検証
- [以前の仮説を支持または反証する新しい証拠]
```

#### Ghost モード — あなたの語り口で回答

スキャン：全コンテンツフォルダ、`drafts/` と `thoughts/` サブディレクトリを除く（完成記事のみ）。

入力：`save` があれば取り除き、残りを質問として使用。

ステップ：
1. 文体の分析：文の好み・語彙の選択・論述構造・修辞的習慣
2. 質問に関連する既存のスタンスと論点を抽出
3. そのスタイルとスタンスで回答を構成

出力：

**回答** — ユーザーの語り口で。長さはユーザーの典型的な記事の段落の長さに合わせる。

**根拠** — 参照または引用したノート：[[ファイル名]]・引用した具体的な段落またはスタンス。上限 5 件。

**信頼性の注記** — どの部分が明確な vault の根拠を持ち、どの部分がスタイルから推測した延長か。

書き込み先：`{analysis}/ghost/YYYY-MM-DD-{質問の要約}.md`
同日・同質問：`## 追加回答 [HH:MM]` ブロックで追記。

#### Stress-test モード — 論述の圧力テスト

入力：`test:` プレフィックスを取り除き、`save` があれば取り除き、残りをテーマとして使用。

スキャン：テーマに言及しているすべての vault ファイル。

ステップ：
1. テーマに関するすべての論点と主張を収集
2. 各主張の論理構造と証拠を検証

出力：

**主張リスト** — vault で見つかったすべての主要な主張。各件：1 文の主張・出典 [[ファイル名]]。

**弱点分析** — 各主張について確認（該当するものだけ列挙）：
- 内部矛盾：異なるファイルが同じことについて異なる主張をしている
- 未検証の前提：証明されていない前提の上に立つ主張
- 論理のギャップ：論証の中間ステップが欠けている
- 証拠のギャップ：主張を裏付けるデータや事例が不足
各弱点は具体的な [[ファイル名]] と段落を引用。

**総合評価** — 堅牢度：堅固 / おおむね堅固だがギャップあり / 大幅な補強が必要。優先的に対処すべき 1〜3 つの弱点。

書き込み先：`{analysis}/stress-test/YYYY-MM-DD-{テーマの要約}.md`
同日・同テーマ：`## 追跡更新 [HH:MM]` ブロックで追記。

#### 共通ルール

- 20 を超えるファイルが見つかった場合は上位 20 件をリストし、総数を注記
- すべてのファイル参照は [[wiki link]] 形式
- タイムスタンプはローカル時間 HH:MM（24 時間制）
- save の有無にかかわらず、端末に完全な分析結果を出力
- 書き込み時：プレビューと完全パスを表示、確認後に実行、実行後に実際のパスを表示
- フォルダが存在しない場合は作成して完全パスを表示

## アクションプランニング

### `/hirameki:harvest [save]`

**目的：** 既存コンテンツから実行可能なアイデアを収穫。
**入力：** オプションの `save` でファイルに書き込み。
**必要なフォルダ：** analysis・daily-notes・inbox + 全コンテンツフォルダ。

スキャン：全コンテンツフォルダ・daily-notes（直近 30 日）・全 inbox。

出力 — 7 カテゴリ、各最大 5 件：

**書ける記事** — 今すぐ記事として発展させるだけの素材があるテーマ。各件：提案タイトル・素材ソース（[[ファイル名]] リスト）・執筆前に何が必要か。

**作れるツールまたはプロジェクト** — ノートで言及されたツールのニーズ・ワークフローの痛点・具体的なプロダクトアイデア。各件：説明・ソース・推定複雑度（小 / 中 / 大）。

**研究すべきテーマ** — 言及されたが深掘りされていない外部の概念・理論・技術。各件：テーマ・vault での文脈・なぜ研究する価値があるか。

**連絡すべき人またはコミュニティ** — 言及されていて現在の方向性に関連する人物・組織・コミュニティ。各件：名前・vault での文脈・連絡する理由。なければ「なし」と記入。

**別のメディアで表現したいアイデア** — 別のフォーマット（動画・ビジュアル・講演・ニュースレター・podcast など）の方が向いているコンテンツ。各件：アイデアの要約・推奨メディア・なぜそのフォーマットがテキストより合うか。

**まだ取引していない価値** — まだ収益化されていない専門知識やスキル。各件：スキルまたは知識の説明・可能な収益化の形（コース・コンサルティング・プロダクト・ライセンス）・vault の根拠。なければ「なし」と記入。

**卒業できるアイデア** — 独立したノートになれるだけの密度を持つ半成形アイデア。各件：出典場所（[[ファイル名]] + 段落の説明）・核心的な主張（1 文）・推奨する送り先コンテンツフォルダ・関連する既存ノート。

卒業の基準：明確な核心的主張がある（質問や思いつきだけではない）・vault の少なくとも 1 つの既存テーマと関連している・十分なコンテンツ密度がある（1 文以上）。

### 卒業フェーズ（save の有無にかかわらず常に 2 フェーズ）

候補リストを表示後に停止し、ユーザーがどれを実行するか選択するまで待つ。

各選択されたアイデアについて：
1. 作成する完全パスを表示、再度確認を待つ
2. 選択されたコンテンツフォルダに新しい markdown ファイルを作成：
   - タイトル
   - 核心的な主張

## 創作

### `/hirameki:frame {アイデア} [save]`

**目的：** 制作前チェックポイント — 労力を投じる前にコアアイデアを検証する。
**入力：** 必須 — 記事のアイデア・製品コンセプト・デザイン方向、または既存のドラフトへのパス。
**必要なフォルダ：** 全コンテンツフォルダ + daily notes + journal。

記事・製品・デザイン・あらゆるクリエイティブ出力に適用。

#### フェーズ 1：アイデアの把握

入力シグナルからタイプ（記事 / 製品 / デザイン）を検出。ファイルパスの場合はファイルを読んで論点を抽出。論点とタイプを出力してから続行。

#### フェーズ 2：5 問フレームテスト

**Q1 — Only-I テスト**：「これについて、私にしか言えない・できないことは何か？」vault 内の固有の経験・スキル・立場をスキャン。評価：強い / 弱い / なし。

**Q2 — 衝突スキャン**：「すでに似たようなものを作ったことがある？」コンテンツフォルダとドラフトをスキャン。2 つの層：
- **Tier 1（発表済み）**：各衝突に対して判定 — absorbed（吸収済み）/ adjacent（隣接）/ superseded（更新）。Tier 1「absorbed」衝突は KILL のシグナル。
- **Tier 2（ドラフト）**：判定 — competing（競合）/ adjacent / feeds（素材提供）。CONSOLIDATE の問いを引き起こす。

**Q3 — 賭け**：「これに触れた後、読者/ユーザーにとって何が変わる？」評価：リフレーム / ツール提供 / 挑発 / なし。「情報提供のみ」= 賭けが低すぎる。

**Q4 — 緊張**：「驚くべき、反直感的、または不快な部分は何か？」緊張なし = サマリー、創作ではない。

**Q5 — 証拠**：「何がこれに信憑性を与えるか？」評価：体現（直接経験）/ 調査済み / 推測的。

#### フェーズ 3：判定

| 判定 | 条件 |
|------|------|
| **PROCEED** | Q1 強 + Q3/Q4 のどちらか強 + Tier 1 absorbed 衝突なし |
| **RETHINK** | Q1 弱、または Tier 1 adjacent 衝突、または Q3「情報提供のみ」 |
| **KILL** | Q1 なし、または Tier 1 absorbed 衝突、または Q3 と Q4 の両方が空 |
| **CONSOLIDATE** | 同じ論点をカバーする Tier 2 競合ドラフトが複数 |

ルール：判定を和らげない。KILL は停止を意味し、方向転換ではない。完全な分析をターミナルに出力。`save` ありで `{research}/frame/YYYY-MM-DD-{idea-slug}.md` に書き込む。frame はコンテンツを生成しない。

### `/hirameki:critique {ファイル|テキスト}`

**目的：** マルチモデル文章クリティーク。
**入力：** 必須 — ファイルパス・[[wikilink]]・または貼り付けたテキスト。
**必要なフォルダ：** vault（wikilink 解決）・`_writing_lab/benchmark/`（出力）。

#### フェーズ 1：テキストの読み込み

入力を解決：ファイルパス → 読み込み；[[wikilink]] → vault で検索して読み込み；貼り付けテキスト → 直接使用。3000 文字超の場合は一時ファイルに書き込み、パスを評者に渡す。

#### フェーズ 2：3 モデル並列レビュー

3 つの次元を各 1–10 点でスコアリング：
- **感官密度** — 読者は描写されているものを見たり・聞いたり・嗅いだり・味わったり・触れたりできるか？
- **構造的緊張** — 文章は読者を引き付けて前に進ませるか？
- **共鳴** — 感情的に届くか？読者は明日も覚えているか？

**評者 1：Claude Opus**（Agent サブエージェント）— 全体品質・構造的流れ・感情の着地。

**評者 2：Codex CLI**
```bash
codex exec "Review this writing. Score three dimensions (sensory density, structural tension, resonance) each 1-10. Then list: strongest line, weakest line, one structural suggestion, one thing to cut. Output in the vault language. Text: $(cat /tmp/critique-input.txt)"
```
失敗時：Claude Sonnet サブエージェントにフォールバック（注記）。

**評者 3：Gemini CLI**
```bash
gemini -p "Review this writing. Score three dimensions..." < /tmp/critique-input.txt
```
失敗時：Claude Haiku サブエージェントにフォールバック（注記）。

#### フェーズ 3：統合

比較表（Opus / Codex / Gemini / 平均）、コンセンサス、差異（3 点以上の差）、最強の一文・最弱の一文・推奨編集。

#### フェーズ 4：保存

`{vault}/_writing_lab/benchmark/YYYY-MM-DD-{title-slug}-critique.md` に書き込む。frontmatter にスコアを含む。

ルール：差異が最も価値ある部分 — 重点的に表示。礼儀のためにスコアを軟化しない。最強/最弱の一文は実際のテキストを引用。

## 外部

### `/hirameki:mekiki {github-url}`

**目的：** GitHub リポジトリを分析し、転用可能なテクニックを抽出して採用適合度を評価。
**入力：** 必須 — GitHub URL（`https://github.com/owner/repo` または `owner/repo`）。
**必要なフォルダ：** research フォルダ（出力）。

#### フェーズ 1：取得（並列）

```bash
gh repo view owner/repo --json description,url,stargazerCount,primaryLanguage,updatedAt
gh api repos/owner/repo/readme -q .content | base64 -d
gh api repos/owner/repo/git/trees/HEAD?recursive=1 -q '.tree[].path' | head -150
```

ファイルツリー取得後、3–5 件の主要ソースファイルを特定して取得。

#### フェーズ 2：分析

**Track A — テクニック抽出**（常時実行）：興味深い部分ごとに抽出：パターン名・何か（1〜2 文）・なぜ興味深いか・転用先（ユーザーの実際のプロジェクト）・アクション（「覚えておく」ではなく具体的な次の一手）。標準的なプラクティスや言語固有の慣用表現はスキップ。

**Track B — 採用評価**（純粋なパターン/デモ repo は除く）：ユーザーの CLAUDE.md とプロジェクトメモリを読んで実際のツール名を確認。リポジトリをツール / フレームワーク / ライブラリ / パターンに分類。比較表を作成（機能 / リポジトリが提供するもの / 現在使用しているもの / 差分）。判定：**adopt**（次のステップ + タイムライン付き）/ **defer**（トリガー条件付き）/ **reject**（代替案付き）。

#### フェーズ 3：検証（Sonnet サブエージェント）

確認：完全性・根拠（未検証の主張なし、実際のツール名、測定可能な差分）・実行可能性（各判定に次のステップあり）。失敗があれば修正してから提示。10 ファイル未満の小規模 repo はサブエージェントをスキップ。

#### 分析後

- **adopt**：クローン/インストールを提案し、vault ノートを `{research}/mekiki-{repo名}.md` に保存。`tags: [mekiki, adopt]`、`status: reference`
- **defer/reject**：簡潔な vault ノートを `{research}/mekiki-{repo名}.md` に保存し、将来のセッションで再評価しないよう決定の根拠を記録

## メンテナンス

### `/hirameki:tidy [tags|fix|full]`

**目的：** frontmatter プロパティの監査とクリーンアップ。
**入力：** オプションのモードフラグ — 下表参照。
**必要なフォルダ：** 全コンテンツフォルダ + inbox + daily-notes。

**モード：**

| 呼び出し方 | 実行内容 |
|-----------|---------|
| `tidy`（引数なし） | 欠落フィールド + 一貫性チェック |
| `tidy tags` | タグ収束分析のみ |
| `tidy fix` | 欠落フィールド + 一貫性 + 自動修正 |
| `tidy full` | 全チェック |

選択したモードのブロックのみ実行。未実行のブロックはレポートに表示しない。

スキャン：
- 全コンテンツフォルダ（再帰的）
- inbox — 全ファイル
- daily-notes — 直近 30 日

**チェックブロック：**

**欠落フィールド**（tidy / fix / full）— frontmatter のないファイル、`tags` または `status` が欠落、タグ配列が空

**一貫性**（tidy / fix / full）— 無効な `status`/`source` 値（source 許可値：self・claude-code・agent・external）、タグの大小文字の不一致、アンダースコア vs ハイフンの不一致、`topic` がタグと重複

**冗長性**（full のみ）— 6 個以上のタグを持つファイル、`created` フォーマットの不一致

**タグ収束**（tags / full）— 上位 10 コアタグ・意味的に類似したタグのマージ候補・孤立タグ（1 回のみ使用）

**出力：** 健全性レポート（問題のないファイル数 / 総ファイル数）。実行したブロックのみ表示。

```
# Frontmatter 監査レポート

> モード：[tidy / tags / fix / full]
> チェック時間：YYYY-MM-DD HH:MM
> スキャン範囲：[スキャンしたディレクトリ]
> スキャンファイル数：N

## 欠落フィールド（N）      ← tidy / fix / full
...

## 一貫性の問題（N）        ← tidy / fix / full
...

## 冗長性の問題（N）        ← full のみ
...

## タグ概要                 ← tags / full
### コアタグ（上位 10）
| タグ | 件数 |

### マージ候補
- `ai_alignment` → `ai-alignment`

### 孤立タグ（1 回のみ使用）
| タグ | 使用場所 |

## サマリー
- 実行ブロック：[一覧]
- 要修正：N ファイル
- 健全性：N%
```

**fix モード**（入力に `fix` が含まれる場合）：

自動修正可能（完全な変更リストを表示して確認後）：
- 欠落している frontmatter スケルトンを追加
- タグの大小文字を統一（多数決）
- タグのアンダースコアをハイフンに統一
- タグと重複する `topic` を削除

個別確認が必要：
- 意味的に類似したタグのマージ
- 6 個以上のタグのトリミング
- 孤立タグの削除

修正後、健全性スコアを再計算し、差分サマリーを出力。

**書き込み動作：** 常にレポートを `{analysis}/tidy/YYYY-MM-DD.md` に書き込む。同日は追記（変更サマリーと健全性スコアの変化を含む）。

1 回あたり最大 50 件の問題を報告。超過する場合は総数を表示して分割処理を提案。

## 作業推論ログ

### `/hirameki:journal {説明}`

**目的：** 作業ログと思考記録。
**入力：** 必須 — トピックの説明。
**必要なフォルダ：** logs + 全コンテンツフォルダ（関連ノートの検索に使用）。

スキャン：
- 現在のセッションの操作
- トピックに関連する vault ノート
- logs にある今日の既存 journal ファイル

ロジック：
1. `{logs}/` で今日の `YYYY-MM-DD-*.md` ファイルをスキャン
2. ファイル名とタイトルを入力のトピックキーワードと比較
3. 明確なマッチ → 追記モード
4. 曖昧なマッチ → 候補をリスト、ユーザーに確認
5. マッチなし → 新規作成モード

**新規作成モード** — `{logs}/YYYY-MM-DD-HHMM-{トピックの要約}.md` に書き込み（HHMM は作成時のローカル時刻、コロンなし；スラッグの言語は `language` 設定に従う：繁體中文なら中国語、日本語なら日本語、English なら英語；スペースはハイフンに置換）：

```
# {トピック}

> 作成時間：YYYY-MM-DD HH:MM

## 背景
なぜこれが起きたか。vault に関連する既存ノートがあれば [[wiki link]] で引用。

## 何をしたか
具体的な操作と意思決定、因果の流れ。

## なぜこのアプローチか
主要な意思決定の根拠。トレードオフ：何を選び、何を捨てたか。

## インスピレーションのつながり
他のアイデアとの接続、トピック横断のリンク。関連ノートに [[wiki link]]。なければ「なし」と記入。

## 改善の可能性
未探求の方向性・代替案・潜在的リスク。なければ「なし」と記入。

## 未完了とフォローアップ
フォローアップが必要な項目。すべて完了なら「保留項目なし」と記入。
```

**追記モード** — 末尾に追加：

```
---

## 追記記録 [HH:MM]

### 何をしたか
[新しい操作と意思決定]

### なぜこのアプローチか
[新しい意思決定の根拠]

### インスピレーションのつながり
[新しいつながり。なければ「なし」と記入]

### 改善の可能性
[新しい方向性。なければ「なし」と記入]
```

「未完了とフォローアップ」セクションも確認 — 完了した項目には完了タイムスタンプを付ける。

## 意思決定サポート

### `/hirameki:decide {テーマ}`

**目的：** 意思決定前スキャン。コミットする前に vault の関連コンテキストをスキャンし、決定の構造を提示する。
**入力：** 必須 — 検討している決定。
**ファイルには書き込まない。** 保存したい場合は `/hirameki:journal` を続けて実行。

スキャン：全コンテンツフォルダ + 直近 14 日の daily notes と journal。

**3 層出力：**

**現状** — vault が知っていること。可逆性の判定を含む：
- **両方向ドア**：間違えても戻れる — 行動バイアスを持つ
- **一方向ドア**：戻りにくい — ここにより長く留まる価値あり

**詰まりポイント** — 逆算法：この決定が確実に失敗する条件は何か？そこから逆算して本当の張力を探す。

**核心の問い** — 1 つの問い。これを知れば決定が明確になる。提案ではなく、選択肢のリストでもない。

```
# 意思決定スキャン：{テーマ}

> スキャン時間：YYYY-MM-DD HH:MM
> 関連コンテキスト：[[ノート1]], [[ノート2]]
> 可逆性：両方向ドア / 一方向ドア

## 現状
[vault コンテキスト、出典参照付き]

## 詰まりポイント
[張力の所在；逆算法による失敗条件]

## 核心の問い
[1 つの問い]
```

ルール：vault に関連コンテキストがほとんどない場合は明示する — 埋め合わせしない。「〜をお勧めします」は書かない。核心の問いは必ず 1 つだけ。
